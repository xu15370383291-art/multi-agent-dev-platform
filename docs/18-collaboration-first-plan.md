## 1. 决定与范围

用户确认先打通七类 Agent 的业务流程，再完善通用恢复。保留原阶段编号用于历史追溯：M1 → M3 协作闭环（含必要执行保护）→ M2 完整执行可靠性 → M4 正式工作台 → M5 综合验收。不把 M3 提前解释为 M2 已完成，不删除任何原恢复验收项。

七类角色是 Supervisor、Product、Architect、Web Developer、Game Developer、QA、Code Reviewer。按项目类型和任务需要选择开发角色；一个纯 Web 项目不必强行调用 Game Developer。阶段验收通过游戏和 Web 两类项目覆盖七类角色。

## 4. 必须先保留的执行保护

- 一个运行只有一个有效协调租约；并行的是该协调者分派的任务，不允许两个 Worker 并发驱动同一主图。
- 调度、工具意图和结果持久化；以稳定 execution_id/tool_call_id 和数据库约束防重复。租约失效后拒绝工具和集成写入。
- 并行前原子预留运行预算和资源额度，结束后结算；新任务、修复、冲突解决、重规划及模型纠正共享原运行总预算，不隐式扩大 M1 限额。
- 开发任务只能写自己的工作目录；共享仓库/集成分支由统一控制端维护。worktree 的 .git 链接及公共对象库不能导致任务获得修改其他任务或宿主仓库的权限；实施前用容器内 Git 和导出/导入方案做真实验证，不能直接暴露宿主路径求方便。
- 继续保留断网、普通用户、无宿主挂载/socket、CPU/内存/PID/日志/路径边界；并行需要总资源准入，不能只限制单容器。
- 取消请求先停止新增派发；结果 unknown、失去租约、无法确认活动容器或副作用时暂停受影响执行及其下游，禁止盲目重放。此阶段可以停下来等待核对，不承诺通用自动接管。
- 配置在执行开始时快照；修改绑定只影响后续新执行，日志明确来源和 revision。活动调用链不偷换模型、不把内容自动发往另一供应商。

并发额度采用原蓝图受限批次，先单并发验证调度，再以可配置上限 2 作为首次并行验证目标。该数值属于待 C0 固化的工程配置方案；实施前记录宿主资源准入及总量限制。资源不足时明确排队或报告未验证，不能串行运行却声称已验证并行。需要增加总预算、开放网络或放宽隔离时另行说明并取得确认。

## 5. 计划、集成、质量与审批协议

计划为不可变版本，任务记录保存所属计划、批准 PRD/架构、任务角色、依赖、AC、范围/接口、基线 SHA。新计划通过代码校验后启用，原执行不被覆盖；重规划不能令活动旧执行继续提交到新计划。控制权、停止活动执行和基线切换无法核实时暂停，不依赖尚未实现的通用恢复。

任务成功与成果集成是两个事实。只有成功并完成必要集成的成果才能解锁依赖；独立分支完成不直接成为交付候选。项目集成写入串行，冲突解决形成受控任务、真实 diff 和新提交，检查失败保留原成果并阻断下游。

质量并行须处理现有 Reviewer 引用 QA 证据的依赖：QA 执行和 Reviewer 源码初审可以在同一固定候选上并行；最终 Reviewer 必须读取该候选当前 QA 结果并生成完整报告。初审不能直接当作最终通过，不能为追求并行删除 qa_report_id/asset_hash/环境关联要求。初审、终审调用均真实计量。

代码修复生成新任务/执行，关联 defect、parent_candidate、原任务和修复轮次；生成新候选后完整重验，不覆盖原 SHA、报告或测试失败。测试资产错误、基础设施错误、产品缺陷分开处理，不让业务 Agent 通过删测试修好验收。

Supervisor 可以提出修复、继续或重规划；实际权限、依赖、审批和交付由程序判断。批准范围内的修复自动推进；需改变 PRD/架构/验收标准时走新版本审批，不能通过重规划绕开用户。
