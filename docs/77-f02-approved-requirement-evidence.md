# F02：批准要求与实际测试证据的对应修复

2026-10-27，承接docs/75的F02。用户授权修复平台共用机制，真实项目继续按用户决定暂停；不重试未知请求、不调用收费模型、不编辑正式业务源码或98条原脚本。F03—F09不因本轮专项而计为完成。

## 已确认的缺口与实施选择

已有机制会校验AC编号、批准原文、实际断言行列及分支字段，也有独立覆盖复核。但是，原独立复核可以仅返回`supported_ids`，没有强制提交“批准要求→前置条件/操作→实际观察与期待→执行断言”的对应证据；三种分支字段存在也不等于完整原要求已覆盖。

本次扩展**现有独立覆盖复核**，不增加Agent、不增加模型审查阶段、不建立另一套业务需求。语义判断仍由独立审查负责；控制端确定性校验来源、位置、版本、声明一致性和缺口，不能声称算法可以证明任意自然语言需求。

## 关键边界

- 源锚点是**静态代码来源**，不自动证明操作、前置或条件分支实际执行。断言还须与控制端实际执行位置对应；已知`if(false)`等不可达来源不能充当操作证明。动态前置状态是否正确、页面状态与见证是否一致仍属于F03及原运行时合同。
- 正常/异常/边界、名称与正文是否对应、完整批准原文是否全部覆盖，必须由原独立审查明确给出判断与理由。控制端会拦截缺失或相互矛盾的判断；不会用关键词规则、场景数量或固定业务答案替代语义判断。
- 原批准的建议、可选措辞不能扩成必测硬要求；目录引用原文，不新增自动批准的子需求。审查无法确认时保留缺口，不能为了schema合法伪造执行。
- 元数据缺失/篡改/版本不符不能降级为通过；不改QA原业务断言、失败史、审批、源码或旧ZIP。发现新的覆盖缺口仍走原补测、审批及修复规则。
- 只向逐项审查传本AC的源锚点，汇总复核只传草稿实际引用case的锚点；完整原脚本和不可变目录仍在原报告。锚点excerpt明确标记截断，完整正文可查，不能把节省传输当作删证据。

## 兼容修复

首次旧链路检查暴露三项返回类型不兼容：显式模型夹具返回ReviewResult基类，原回执入口要求动态逐AC子类实例，即使字段合法也被拒。统一在`result_receipts.call`将BaseModel数据按请求schema重新校验，再保存标准结果；AC字面量、必填字段、范围和证据仍按目标schema严格验证。新增测试确认错AC和空coverage仍拒绝，不能用类型归一化绕过门禁。

旧测试夹具仅补齐新合同下显式、可核对的协议数据；不是生产默认答案，生产模块不导入这些夹具。所有模型为明确夹具的验证，只证明平台控制流程，不代表百炼已经准确理解任意需求。
