# F04：需求优先的失败归因与源码修复入口

2026-10-27。承接docs/75的F04，沿用F01—F03共用机制。用户本轮授权平台专项修复，真实离线清单仍人工暂停；不重试未知请求，不调用收费模型，不改原业务源码、98脚本、批准要求或历史结论。

## 核实的根因与实施边界

原Classification只强制分类、文字理由和源码引用。独立复核也返回这一结构，没有要求逐项绑定批准原文、实际失败位置、期待与合同的关系及相反证据。引用了真实代码，并不能证明QA的期待正确；原按钮完整文案争议正属此类风险。另有`repair.source_defects`兜底路径：Reviewer给出源码位置且QA有执行断言，就可直接创建源码修复任务，绕过完整归因。

本轮将归因证据和源码入口一起约束，不按项目名、按钮文字或某个AC编号打补丁。不增Agent、不换七角色模型、不增独立模型阶段；继续使用既有Supervisor初步归因→Reviewer独立复核→修复方案审查。归因有效不等于业务验收通过。

## 协议与实际处理

`quality-correction-v3`的新归因每项必须提交：同例observation_id、批准AC及原文、合同依据、实际行为、失败类型/锚点、源码分析、期待关系、相反证据状态/引用/分析，以及适用时的控制端环境证明ID。控制端目录绑定候选SHA、批准PRD/架构payload、完整源码、原测试与执行摘要。修复入口重新构建目录，不把模型自填摘要当证据。

已执行失败断言与操作报错分开；setup须匹配实际失败准备证据，unit仅对应-1。相反证据未解、期待未规定/矛盾/不确定时，只能保留needs_human，不允许同时指定该例自动步骤/API修改。真实源码与步骤混合问题可保留source加procedure_cases，源码缺陷仍进入原新任务/新候选流程。新测试的source_gap_evidence明确标为源码检查发现，不能伪称已经执行该测试。

初步提案允许被独立Reviewer纠正；控制端在最终归因核对后、生成任何步骤补丁前拦截未决或矛盾结果，保存两份提案、目录、具体校验错误和未决编号。原正式失败不被改成通过，原断言修改仍走原人工决定边界。

旧v2工作项与旧Assessment序列化保留原形状，可核对已存在的历史任务证据；新ensure不把旧v2当成当前v3归因，新建源码修复任务必须有当前合同。旧审批、已有计划及失败记录不删除，不通过给旧记录补字段冒充重新验收。

边界：结构、引用和执行记录可做确定性校验；“supported”是否真实符合自然语言需求、源码与相反证据含义，仍需独立模型审查。若两次模型都错误地声称支持，结构合同不能提供任意需求零误判保证。现有同一百炼配置的语义准确率和完整自主交付仍须F09真实冻结验收，不因本轮夹具通过而声称已经通过。
