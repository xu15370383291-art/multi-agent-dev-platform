## 1. 用户约束的具体落实

最终端到端验收最多 **2 个业务项目**，不再用4组业务项目重复验收。一个简单Web应用、一个浏览器游戏，覆盖两种Developer。故障注入尽量在相同隔离基线上复用，不把每个测试函数都做成一个真实模型项目。

“所有功能覆盖”以以下需求ID为准，不等于只测两条正常路径，也不等于每个错误都发送一次付费模型请求。明确区分：纯单元/HTTP夹具、真实PostgreSQL/checkpoint、真实Docker/Git/进程、真实模型端到端。模拟不能替代真实模型交付证据；真实模型也不能替代确定性的故障测试。

## 2. 测试分层

- L1：纯分类、schema、状态转换、摘要与权限判定。无模型/业务容器调用。
- L2：独立随机PostgreSQL schema + 实际PostgresSaver + FastAPI；可控模型transport注入429/超时/格式错误等。每个fixture标明模拟部分，禁止写应用表。
- L3：实际Docker/Git/进程故障注入；控制端kill子进程、真实租约/资源槽与可信回执。不执行宿主机业务代码，不杀现有API/Worker/其他项目进程。
- L4：真实前端交互，桌面1440与手机390，既有审批/交付/模型/历史回归，HTTP夹具明确标注；真实端到端由专用测试服务/2个测试项目验证。
- L5：2个小型真实模型项目完整执行与交付，各自只有一次正常开发流程，按设计位置暂停/恢复，不反复创建同类项目。真实模型调用和成本逐项记录。

## 4. 两个真实模型验收项目

### E2E-W：本地计数与记录 Web 应用

需求固定：加/减/重置计数、记录最近操作、刷新保存、存储失败有提示，手机可用。控制规模为一个开发任务，保留产品、架构、Web Developer、Supervisor、QA、独立Reviewer和交付。不得用硬编码预制代码冒充模型开发。

在批准文档后执行一次受控暂停和模型配置切换；复用已核对源码继续，不从需求重跑。两份已验证配置固定revision；若用户仅有一份可用配置，用两份独立修订验证配置切换，跨供应商协议边界由明确transport夹具补足，报告不得称为真实跨供应商通过。没有可用配置时准确列阻塞，不索要聊天明文Key。

验收：真实DOM输入、键盘、手机、刷新与存储异常；开发续接链和新旧模型revision；QA/终审同candidate/SHA；下载ZIP核对摘要并独立运行；事件可追溯。暂停与切换记录不增加项目数量。

### E2E-G：极简网格收集游戏

需求固定：方向键/触屏移动、收集目标计分、边界规则、重新开始；不加音效、联网资源或复杂关卡。保留Game Developer及其余角色真实路径。

审批等待期间重启专用测试Worker；批准后仅继续一次。开发完成和质量/交付保存窗口的底层故障主要在L3完成，不在真实模型流程每次杀进程浪费调用。该项目在一个已经核实的安全边界重启并继续，完整交付；若需要验证QA/Reviewer恢复，复用同候选的已保存资产，不能生成新候选借用旧通过。

验收：真实玩家操作、游戏规则/重开/手机；审批不重复、重启不中断历史；QA与Reviewer当前版本一致；预览、ZIP独立启动和摘要。

两项目共覆盖七种角色，但不强制每个项目都调用Web/Game两个Developer；真正并行分支和故障竞争主要由L3在可控模块基线上验证，不要求为此再建第三个付费项目。

## 5. 成本与执行控制

每项目仍为原默认30次/3600活动秒；schema纠正、恢复续接和质量调用全部计入。开跑前统计既定角色与剩余工作，过程中展示真实用量。没有把“30次以内必能交付”当保证；不足则停止并给出剩余工作，不自行上调或重开同项目清零。

最多创建上述2个真实模型项目。失败后优先在同一项目原预算里修复；旧失败、模型调用和候选保留。专项测试使用独立schema和沙箱，不污染生产项目列表，不使用当前贪吃蛇做破坏性故障注入。

顺序：R1—R5各自专项 → 全量后端及前端回归 → E2E-W、E2E-G → 针对发现的问题修复及相关复测。必需检查通过后不反复跑无新增风险的全部业务项目。

人工输入可由测试自动化完成，不要求computer use；保留真实浏览器操作和HTTP/工具回执，不以直接改DB代替用户操作。生产已有用户审批不会被测试代为确认。专用测试项目的审批按其实际生成文档和验收合同检查后操作，不能无条件自动放行。
