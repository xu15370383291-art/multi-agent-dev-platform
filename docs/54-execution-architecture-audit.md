## 已实施的合同

1. `integration_diagnostics`独立核对合并/构建进程与不可变回执，核对构建输入、输出/结果、恢复可信Git后的归档及未推进的共享基线；错误信息/源码任意一处对不上就不授权。签名确认的预备构建失败也可分析，不要求一定有shell退出码。这个结果仅授权诊断，不能把失败任务送给finish_completed重复合并。
2. 初次失败和恢复后的主管都获得真实构建日志、批准PRD、完整架构及原任务scope/non_goals。架构提示消除“局部测试通过即可集成”的误导：每次合并完整构建仍必须通过，入口与跨模块接口应在对应阶段就绪。
3. 免费检查登记`integration_build_diagnosed`事实，按源码语义/任务范围/验收关联/实际失败结果形成稳定摘要；新操作ID、措辞、调用计数或Git空提交不能产生额外诊断机会。主管进展检查认识该事实，同一诊断幂等；自动续接绑定诊断摘要，新的实际失败不会被前一任务的重试key误拦。
4. 原run/thread可以通过人工`open-recovery`打开：等待审批只恢复相同检查点对应的同一有效文档，绝不自动批准；暂停/失败/取消转入人工核对状态，旧取消时间/状态、取消任务清单留在持久事项和事件中，旧TaskExecution取消状态不改。只有该清单中的取消任务可在原检查后追加子尝试。未知工具结果仍由原回执核对，不因“打开恢复”而变成成功。
5. 新建一轮不再强迫取消旧的暂停/待审批轮次。按项目的数据库事务锁和租约/未停止进程检查串行领取业务工作；不同项目及同一轮内原并行任务能力保留。打开历史恢复仅改变所选轮次，不取消、审批或覆盖另一轮。
6. 默认历史查看只读；显式打开后允许在那一轮继续、审批/切换模型。标签明确历史处理状态，项目卡优先显示正在执行的轮次，不会把“另一轮待审批”误当作当前没有执行。已完成且没有未完成错误的交付轮次保持只读。
7. 真实主管reason校验失败，旧记录仅保留通用validation_error，不能事后确定原字段的具体值。本地用超过5000字符的结果复现了`string_too_long`被降为通用错误的问题。补齐安全错误类型，说明reason只需简短决策依据，保留原5000字段约束和模型配置，不靠扩大调用/输出额度修复；不保存原错误字段内容或密钥。
