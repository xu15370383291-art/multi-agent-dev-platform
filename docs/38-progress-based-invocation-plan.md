# 调用策略改造：正常推进不限总次数，重复与停滞受控停止

2026-10-21。依据用户最新要求：“模型调用次数不应该设置次数限制，只要是在正常进行任务，不进行死循环或者重复调用就可以”。用户已明确批准严格执行本文。本文保留具体实现设计与验收合同，实际完成证据及待办见[docs/39](39-progress-policy-acceptance.md)。M5已验收版本保留，作为后续增强单独实施和验证；旧运行不批量改写。

## 1. 目标与授权边界

新运行以“进展保护”替代60次总调用硬上限。调用次数、token、供应商usage、错误和可能计费的超时继续如实累计，不清零、不隐藏。任意第61次/第100次调用不能单因总次数被拒绝；是否继续取决于取消状态、已批准范围、执行身份、真实进展和异常记录。

本次请求明确改变的是模型调用次数策略，不推定其他资源、审批或验收限制也已取消。3600活动秒、每任务80次工具操作、单工具60秒、模型配置超时、CPU/内存/PID、全系统2槽及隔离规则现状在实现前必须列清；本设计暂不扩大这些限制。前端必须同时显示独立的时间/工具限制，不能把取消次数上限宣传成无限时长。若随后决定将正常任务的总时间/工具次数也改为按进展续期，作为明确的规则调整追加设计，不能在本次暗改。

开发Agent的24轮模型对话上限属于模型调用次数的另一处硬截断，须纳入本次改造：达到观察边界后持久保存会话/检查点并重新评估是否推进；不得仅因达到24轮就失败，也不新建任务清空循环历史。

旧运行保留创建时的策略快照、累计记录和原额度，不批量改写历史或自动恢复暂停项目。需要让某个旧暂停运行采用新规则时，显式登记策略迁移事件，保留旧快照/已用次数/活动时间/失败原因，并重新核对恢复基线。新策略不授权重放未知副作用。

## 2. 三类判断必须分开

| 情况 | 证据 | 处理 |
| --- | --- | --- |
| 正常推进 | 合法新依赖成果、被验证的源码/构建变化、测试执行/缺陷修复结果、有效文档审批或工具观察 | 可以继续，不因总次数停止 |
| 可疑重复/停滞 | 同目标、同输入状态、相同操作或失败模式，连续没有新增有效证据 | 先阻止对应重复动作，解释原因；有限复核仍无可执行新方案时暂停 |
| 确定不能安全继续 | 取消、unknown缺回执、身份/租约过期、越界、批准版本过期、停止未确认、独立资源限制达到 | 按既有规则拒绝/暂停；有进度也不能绕过 |

“新证据”不等于“成功”。一次有必要的失败测试可以提供新的可定位问题；相同失败在相同候选重复执行却没有新信息，不能反复算进展。新源码、日志或文档也不自动意味着目标更接近完成。

## 3. 进度从控制端事实产生

按阶段定义期望成果，关联run/task/plan/document/candidate/role，记录可追踪的证据引用：

- 产品/架构：通过结构和范围校验的新文档/计划、实际处理的用户修订；只有改措辞或版本号不足以持续重置停滞窗口。
- 开发：有意义的变更、必要的新文件/接口观察、与当前缺陷相关的真实工具结果；文件mtime、空提交、注释/空白变化、重复读取同一片段不算实质推进。
- 构建：同输入的构建回执可复用；有源码/锁文件/环境变化，或原执行未完成时，才按合同决定是否需要重新构建。一次新构建失败是新观察，反复同因失败不是。
- QA：新候选/资产对应的真实执行、AC覆盖或失败集合发生有解释的变化；不得通过删除失败用例或改验收门槛制造进度。
- Reviewer/Supervisor：形成与真实证据关联的决定、修复任务、依赖解锁或交付；模型反复输出“继续”不能算进展。
- 依赖等待/审批等待/正在运行的长工具：等待状态不是Agent无进展，不为询问“完成了吗”反复调用模型；使用持久事件和既有调度唤醒。

采用“状态有变化”和“目标有进展”两类信号。换SHA、换任务ID、换模型、增加日志、制造新错误只能说明变化，不能单独证明推进。对探索性阅读允许有界的新观察窗口，不能无限读取不同路径绕过检测。

控制端规则可识别明显重复和停滞，不能声称能够完美判断所有程序修改的语义价值。对复杂但可能合理的探索采取可解释的可疑状态与复核，而不是单次启发式直接终止整个项目。

## 4. 重复动作如何识别

操作指纹至少包含：目标任务/阶段/批准基线、工具操作和规范化参数、输入源码/构建/依赖摘要、当前资产或测试摘要、实际执行环境版本。URL时间戳、调用ID、日志时间等噪声不能成为规避重复判断的依据；也不能粗暴删掉有业务意义的参数。

1. **同幂等键投递**：沿用当前持久回执，未知则核对，不能再次产生外部副作用。
2. **同输入重复请求已知结果**：在版本、环境、角色权限和回执均有效时复用原结果，不再发模型/工具请求；过期结果不能冒用。
3. **合法复验**：源码、候选SHA、测试资产、环境或明确复验原因变化时允许。修改源码后再次运行同一测试命令是正常行为。
4. **有时效/副作用的操作**：不能仅凭参数相同就缓存或重放。是否可复用由工具合同决定；网络恢复的有界重试保留全部尝试与费用不确定性。
5. **往返循环**：识别A→B→A的候选/错误/决策指纹、相同问题反复分配不同Agent、创建修复任务绕过停滞。指纹历史跨重试、子任务、重规划、切模型与重启保留。

## 5. 观察与处置规则（建议初值，不是总次数额度）

| 检测 | 建议初值 | 行为 |
| --- | --- | --- |
| 同状态同动作得到同失败/无变化 | 连续3次形成证据 | 在下一次付费调用或有副作用工具前拦截，提供原回执和重复原因；不发第4次相同请求 |
| 阶段观察窗口无有效推进 | 最近6次相关模型调用 | 进入可疑停滞评估；窗口可包含失败诊断的新信息，不只看是否写文件 |
| 复核 | 同一停滞指纹最多1次Supervisor评估 | 优先本地规则分析；模型评估如有必要计入账本。必须给出有证据的新策略和受限执行窗口，否则暂停；复核本身不能递归触发无限复核 |
| 相同状态集合往返 | 同一循环重复2轮 | 汇总循环链和原始证据，转入停滞处理；新的已验证成果可以打破可疑状态 |
| 网络/结构修正 | 沿用既有限次退避和修正合同 | 只处理对应短暂错误，不因去掉总次数额度变成无限重试 |

这些数值须通过故障测试校准并写入版本化策略。6次是观察窗口，不是“一个任务最多6次”；连续100次实际有效推进可继续。阈值触发后也不无条件关闭整条流水线，先识别具体任务/依赖：仅隔离可疑分支；其余已经授权且独立的分支在既有调度/隔离规则下继续。整个运行无法安全推进或已无可运行分支时才汇总暂停。

不能用“失败计数清零”规避反复失败。检测原始历史始终保留，新的可信进展仅改变当前观察窗口。恢复不因用户点了一次继续就清空停滞指纹；必须有实际输入变化、明确新策略或经过审计的例外。

## 6. 接入现有代码

| 模块 | 必需改动与验收 |
| --- | --- |
| config/db/migration | 新增运行级策略模式与版本快照；新progress_guarded模式模型总上限为null，旧fixed模式必须保留原整数；不使用999999/0等伪无限值。原Invocation消费记录保留 |
| invocation_meter/workflow/plans | 所有角色在模型请求前走同一准入判断，租约内原子登记调用意图、计数和状态证据；固定模式仍核对剩余额度，进展模式不做次数减法。任务预留保留身份/并行准入语义，不再假设每个模式都有总次数余量 |
| developer | 去掉24轮到达即失败，改为持久观察/续接边界；保留消息上下文、真实工具引用、invalid completion处理。提示不再写“余N次，为QA留3次” |
| repair/continuation/quality_revision | 不再以剩余3/5次阻止进展模式的必要修复/质量检查；审批、原AC、候选、新报告和unknown门槛完全保留 |
| 进度检测器 | 汇聚现有文档/计划/TaskExecution/IntegrationRecord/ToolExecution/QualityReport/Invocation，不让Agent自行写入已验证进度；阶段性评估与操作前重复拦截分开 |
| 持久数据 | 保存策略版本、规范化动作指纹、输入版本、结果证据、进度/变化分类、停滞窗口、处置与恢复原因；崩溃前请求已发但结果未知时继续按现有对账阻断 |
| recovery/model_switch/workbench_actions | 双模式兼容、恢复基线包含策略摘要/检测状态；检查旧诊断/按钮/模型切换不会被null额度误判；切模型不重置累计和重复历史 |
| LangGraph/Worker | 不因单节点批次/递归配置达到而伪装业务失败；按当前实际图配置检查并建立持久批次边界，不能直接将所有递归/工具限制设置为无限 |
| frontend/API/OpenAPI | 改为“已调用87次 · 按任务进展执行”，单独显示时间/工具资源和当前任务进展；固定旧运行仍显示46/60。暂停明确列出重复动作/最近有效进展/失败原因/原证据及可用下一步 |
| 运维/备份/发布 | 策略和检测历史随DB配套备份；新安装与旧206升级、旧报告/ZIP/暂停运行兼容；生成新发布版本，不修改M5已验收包 |

统一入口必须覆盖结构化Product/Architect/Supervisor/QA/Reviewer和开发聊天调用，包括修正输出与恢复路径，不能只检查开发循环。防重准入与调用意图在同一租约/事务边界；并行两个调用不能相互把对方的活动误判成停滞，也不能同时绕过同一分支的暂停状态。

## 7. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 新运行连续61/100次有效推进 | 真实调用路径在隔离模型夹具中越过原上限，持续记账、不因总次数暂停；不花费100次真实API来测试数字 |
| 七类角色/结构修正/QA/修复 | 全部走同一双模式准入，无隐藏剩余额度判断；旧固定60第61次仍拒绝 |
| 24轮后仍有效推进 | 正确检查点与继续，不丢消息、不假完成、不重新执行已知工具 |
| 原样调用/同错误循环 | 复用可信结果或拦截下一次；不继续收费空转 |
| 改源码后同命令复验 | 允许真实执行；新SHA/资产/环境准确关联，不误用旧回执 |
| A/B往返/新任务/新模型规避 | 重复历史跨尝试保留，能阻止绕过 |
| 空白/注释/日志/空提交伪进度 | 不持续重置停滞；新增有效读取允许有界探索 |
| 文档审批、依赖、长工具等待 | 不触发无意义模型轮询，不误判死循环 |
| 失败测试提供新诊断/复杂探索 | 不因一次失败就停；疑似停滞可解释、有限评估，无递归复核 |
| 并行/取消/租约失效/unknown | 独立任务判断准确，副作用不重放，暂停/取消后不新派发 |
| 重启/恢复/策略迁移 | 计数、策略、窗口和指纹持久，核对基线正确，不自动恢复旧项目 |
| 原时间/工具资源限制 | 仍真实生效，前端明确显示具体原因，不把有限时长说成无限 |
| 工作台/备份/旧ZIP/旧预算 | 新旧模式都正常，保留全部历史和已验收成果 |

实施顺序：先完成双模式合同与数据库迁移→统一准入及持久进度检测→24轮边界与各角色/恢复路径→界面和暂停解释→隔离全覆盖/旧数据与部署回归→最多复用1—2个适合的真实项目验证完整链路。重复/死循环等高频场景使用明确模型夹具和真实PG/工具回执验证，不消耗大量真实调用；真实验收如需新项目，应沿用约定配置并单列实际消耗。

完成标准：既证明第61次正常推进不会被总次数拦截，也证明明显空转能在继续付费前被挡住；仅把60改成更大整数、null后漏改恢复分支，或只凭模型说“有进展”均不算完成。
