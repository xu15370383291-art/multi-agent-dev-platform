## 1. 目标、范围与不变条件

目标：让个人用户在当前Windows电脑上，按交付说明启动工作台，完成两类项目的需求、审批、开发、质量检查和交付；出现断线、Worker故障、取消或Docker异常时能定位和安全处理；平台与业务成果能备份、恢复和复现。

本阶段是部署补齐、运维能力和综合验收，发现缺陷须修复到对应实现，不能只编写验收说明。

- 保留七类Agent、真实LangChain/LangGraph、统一Tool Gateway、项目隔离、DAG与受控集成、版本审批、持久恢复和固定候选验收。
- 保留默认30次模型调用、3600活动秒、最多2个系统Docker执行槽及现有CPU/内存/PID/网络/日志限制。旧45次特例不推广；额度不足时真实暂停，不创建替代运行绕过。
- 保持个人、本机、无注册/团队的部署边界；不扩展云发布、任意业务后端部署、导入仓库、微信小游戏或交付后迭代产品流程。
- 保持已批准的B方案界面。只增加部署/健康/资源/清理必要说明和操作反馈，不重新设计工作台。
- 不要求computer use。可执行测试和真实浏览器自动化仍必须完成；模型/HTTP夹具不冒充真实模型闭环。

## 3. 按依赖推进的七步工作

### S0：范围盘点与验收合同

1. 建立原始V1要求→M1/M2/M3/M4已有实现→M5检查→证据的总表，核对原2048、审批重提、并行/冲突/修复和unknown场景。
2. 检查当前服务、数据库版本、工作区、执行/QA镜像、凭据引用、端口和磁盘；只读盘点用户数据与专用验收数据。
3. 确认保留/清理方案，列出待确认项；对已有文档的历史状态做“当前状态”说明，不篡改原始上下文或删除门槛。

完成条件：每项必需要求有稳定编号、模块、测试方式；依赖与待决策项明确。规划表不能标记为实际通过。

### S1：可重复的本机部署与启停

1. 提供Windows预检/构建/启动/状态/停止入口，统一路径、端口、依赖、日志位置和配置。模型凭据不由脚本导出。
2. 启动顺序：确认Docker与原数据位置→已有数据库健康→核对迁移→API/预览→Worker→正式前端。首次安装与已有环境升级必须区分。
3. 启停记录本平台进程身份和启动参数；重复启动不产生重复Worker，不接管未知占用端口；停止不误杀其他项目，不删除数据库卷。
4. 完成前端生产构建与本机静态托管、API地址及独立预览来源配置，验证刷新、SSE、下载、历史路由及手机布局。
5. 提供脱敏环境变量示例、锁文件与执行/QA镜像构建和校验说明；离线业务容器不临时安装任意依赖。
6. 将本次Docker经验纳入预检：本机原数据盘为`D:\docker\DockerDesktopWSL\disk\docker_data.vhdx`。Docker显示空库存时必须阻止“升级已有环境”，指导核对原盘；不自动改Docker设置、恢复出厂、删socket/卷或注销WSL。

完成条件：全停后按说明正常启动；重复启停、端口冲突、Docker不可用、数据库不可用、迁移不符有准确反馈。核心使用不依赖手工拼接多个终端命令。

### S2：备份、恢复与升级演练

1. 定义备份清单：DB及检查点、项目源码/版本库/回执/报告/交付文件、必要配置、代码/依赖/镜像标识；逐项摘要与格式版本。
2. 明确一致性窗口：停止新增派发、确认活动任务已停止且无未知副作用、停止写入，再备份；不以“只导出DB”代表完整可恢复。
3. 将备份恢复到独立数据库/工作区/端口，禁止覆盖公共环境；同机凭据引用可核验，换用户/机器时明确须重新录入并验证模型配置。
4. 恢复后读取旧项目、审批、暂停原因、事件和ZIP；审批等待/暂停运行保持原状态，未显式继续前模型调用为0。
5. 演练文件缺失、摘要不符、版本不兼容、备份中断；失败不污染现有运行环境。
6. 发布升级流程保留备份与迁移前后摘要；回退演练采用兼容旧代码或恢复到隔离环境，不删除206序号历史。

完成条件：实际完成一次完整隔离恢复并留下原始回执；不是仅验证备份文件能列出目录。

### S3：资源、保留与清理保护

1. 汇总DB、项目文件、日志、交付和本平台容器的使用量；标记无法可靠计算的部分，不宣称精确全盘统计。
2. 核对工具输出截断、工作区/归档限额、超时、预算、并发槽；补齐发现的无界写入和错误反馈，资源不足时暂停并保护证据。
3. 检查预览停止、服务停启及任务容器生命周期；停止预览不能删除ZIP或把已交付结果改为未完成。
4. 清理候选需绑定项目/运行/执行身份、最终解析路径和当前依赖；禁止符号链接/重解析点越界，禁止通配扫描后直接删除。
5. 活动、待领、审批等待、paused/unknown、恢复依赖、有效候选、报告及交付引用全部受保护。即使没有进程，也不能把它们当无用缓存。
6. 清理预览与执行间重新校验，拒绝过期清单；先在专用测试数据中验证幂等、部分失败、并发恢复与审计记录，再按获批规则开放显式操作。公共历史、本次Docker原盘与其完整备份不作为测试清理对象。

完成条件：既能说明“什么可清、为什么”，也证明“什么不能清”；所有删除能力受已确认策略约束。

### S4：跨阶段故障与安全回归

按第4节矩阵验证审批、并行/集成、持久恢复、模型切换、隔离、资源与交付。使用真实PostgreSQL、Docker、Git、HTTP/SSE和进程故障注入；模型输出夹具仅用于可重复触发边界，并明确标注。

先保存失败证据，再修复对应模块，复测失败项及关联回归。不得通过降低AC、跳过断言、清空检查点、换运行清零预算或重写旧报告解决失败。

### S5：最多两个真实模型项目

- 项目A：2048，覆盖规则与计分、方向输入、重开、最高分、键盘/触摸及移动布局；具体AC以真实批准PRD为准，不能硬编码产品输出。
- 项目B：简单Web应用，例如带筛选和本地保存的事项管理，覆盖表单校验、增删改、状态/筛选、持久化与中文/空状态；具体范围以批准PRD为准。
- 从正式构建工作台提交需求；实际阅读并按版本处理PRD与架构，至少覆盖一次合理修改重提。保存批准版本与摘要，不用自动批准未阅读的文档。
- 两项目合计验证Web/Game两种开发角色以及Supervisor/Product/Architect/QA/Reviewer；至少一个项目使用合理的独立任务与依赖，不为测试而要求全部角色出现在同一项目。
- 固定候选实际构建、QA与独立Reviewer通过后，校验ZIP全文件摘要，在独立静态服务上实际操作桌面与手机；项目源码检查与构建放在受控Docker内。
- 真实模型输出不保证自然触发冲突、unknown和修复；这些场景必须由S4确定性专项覆盖，不能因两项目成功而省略。
- 审批等待或可核实的安全节点演练重启/断线；故障注入优先隔离环境，不对公共活跃项目破坏性操作。失败在原项目中诊断并修复，最多2个项目不以删库重建规避。

完成条件：两类完整真实闭环及独立交付通过；调用次数、供应商/模型修订、运行ID、候选SHA、报告和原始回执齐全。如预算/模型/环境阻塞，登记未验证，不能扩额或用历史成果冒充本轮新运行。

### S6：V1发布与操作文档

1. 运行最终全量后端、前端、构建、静态检查、迁移检查和关联集成测试；变更后执行与风险相称的复测，去重统计。
2. 发布版本记录代码清单/摘要、数据库版本、锁文件、镜像ID和配置格式；当前仓库存在未跟踪文件，不能只用`git archive HEAD`打包造成漏文件，也不能宣称已经提交版本。
3. 交付部署说明、示例配置、日常使用、备份恢复、故障处理、资源与清理说明、已知限制和总验收报告。
4. 若有必需项失败、缺证据或规则未确认，发布结论为未通过/受阻，列明下一步；所有门槛满足后才标记M5与当前约定V1完成。

## 5. 测试分层、证据和停止条件

1. 单元/API/前端测试：精确覆盖版本、幂等、状态、动作权限、清理候选与错误反馈；注明模型/HTTP夹具。
2. 真实集成：隔离schema/工作区/端口，真实PG/Docker/Git/进程/HTTP/SSE；注入故障，核查持久记录和副作用，而非只检查固定错误文本。
