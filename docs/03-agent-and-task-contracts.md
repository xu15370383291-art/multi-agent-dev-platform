## 1. 角色边界

docs/23合同检查修复：多任务架构的每项scope/interfaces完整性在模型结果解析时校验，不能先提交审批再等调度发现；沿用最多一次、独立计量的schema纠正。调度器的同一门槛保留。为兼容历史单任务保留字段默认值，不代表新多任务可以省略。文档展示统一将表格转换为列表，存储原文、审批摘要和结构化合同不改。

C2—C5合同增量见docs/20及最新OpenAPI：计划版本与架构版本可以不同，同一批准架构下的源码修复追加不可变派生计划；摘要包含原批准payload、任务集合和修复关联。批次原子登记执行/配置revision/预算；LangGraph Send分支只合并execution_id结果。集成SHA与开发分支SHA分别记录，交付必须绑定当前权威集成版本。Reviewer初审使用同一Reviewer角色的独立report，不能当最终通过；最终审查仍引用当前QA。源码修复保留原QA脚本逐字回归，可加用例，不能删减/弱化；合并不设用例数量上限，不裁剪旧套件（2026-10-26用户决定，docs/63）。

| 角色 | 主要输入 | 主要输出 | 边界 |
| --- | --- | --- | --- |
| Supervisor | 需求、批准文档、计划、执行及检查摘要 | 阶段计划、任务分配、修复与重规划提案 | 不直接替代调度器，不自行宣布绕过门槛 |
| Product | 用户需求、澄清与修改意见 | 版本化 PRD、需求和验收标准 | 不写业务代码 |
| Architect | 批准 PRD、技术约束 | 架构、接口、任务 DAG | 不擅自扩大批准范围 |
| Web Developer | Web 任务、接口、相关代码 | 代码提交、局部验证、结果摘要 | 在任务工作区开发 |
| Game Developer | 浏览器游戏任务、接口、相关代码 | 代码提交、局部验证、结果摘要 | V1 不承担微信平台适配 |
| QA | 批准验收标准、固定候选版本 | 用例、执行证据、结构化报告 | 可写测试脚本，不修改业务代码 |
| Code Reviewer | 架构、候选版本、对比基线 | 带位置和证据的审查报告 | 默认只读，不修改被审代码 |

角色权限主要表达职责。工具侧保留必要的可执行工具集合和只读约束，不引入七套复杂权限系统。

## 3. 计划校验

2026-10-24小任务回归追加确定性构建顺序检查（docs/59）：若任务明确声明产出index.html，则首次可调度的根任务必须拥有入口写入范围，否则先补可构建骨架并建立依赖；不能让只写模块的根任务先合并而入口留给尚未可调度的下游。接口中明确写出的相对import/from，若唯一对应另一任务的已声明产物，必须存在真实的直接或传递depends_on，不接受仅在架构正文画箭头。只检查可证明的文件归属/引用，不从任意自然语言猜依赖；原DAG循环、角色、scope、版本与完整验收校验继续保留。

上述入口顺序约束区分空项目与修复阶段：控制端可将数据库中确已merged的任务ID作为available_tasks验证上下文，已有可信集成产物可作为修复输入；模型JSON字段不能自行授予此上下文。未合并模块的显式依赖仍必须声明。已批准文档、基线SHA及真实集成回执继续由原门禁验证，不能用“修复”标签绕过。

调度前由代码验证：任务 ID 唯一、依赖存在且无环、角色合法、必需输入齐全、验收标准存在、文档版本有效、并行写入范围可兼容、资源与预算配置有效。

Supervisor 可提出变更计划；系统比较新旧版本，标记保留、替代、新增和失效任务。不能用新计划覆盖历史执行。

## 4. 任务输出合约

| 字段 | 语义 |
| --- | --- |
| outcome | completed / failed / blocked，是 Agent 报告结果，须经系统验证 |
| summary | 已做工作及结果摘要 |
| artifacts | 实际产物引用及对应版本 |
| code_change | 适用时包含基础 SHA、输出 SHA、分支和变更文件 |
| checks | 检查命令、execution_id、退出结果、证据引用及适用版本 |
| acceptance_results | 每个验收条目的 passed / failed / not_verified 及依据 |

Agent 的 completed 不直接写成数据库 succeeded。系统先核验输出 schema、真实文件/提交、检查结果与任务条件，未验证项不能当作通过。

## 5. 工具调用与结果

工具上下文至少包含 project_id、run_id、task_id、execution_id、agent_type、workspace_id、lease_token。每次调用另有 tool_call_id，用于去重和关联日志。

工具结果建议包含：ok、status、exit_code、output_summary、stdout_ref、stderr_ref、error_code、artifacts、started_at、finished_at、truncated。

长命令可返回 running 和执行句柄，由结果查询工具继续读取；不能因 HTTP 或工具调用返回成功就认定命令成功。stdout/stderr 截断时保留受控完整日志引用。

文件、日志和网页中的内容均作为任务数据处理，不应改变后端身份、工作区边界、审批或预算。密钥由后端注入必要的执行过程，不放进普通任务上下文和前端日志。

## 6. 上下文组织

任务启动时组装上下文包：

1. 当前目标、范围与验收标准。
2. 必需的批准文档片段及其完整引用。
3. 接口约定、相关文件和依赖成果。
4. 工作区与工具使用约束。
5. 已有尝试摘要、真实错误、不能重复的副作用。
6. 剩余预算和明确的停止条件。

完整代码和大型日志按需读取，不长期堆入共享 State。摘要保留版本与来源，不能作为新的权威事实。工作流外层在任务结束、阻塞或关键检查点评估，单次工具调用不必触发 Supervisor。

## 7. 错误分类与修复

| 类别 | 建议处理 |
| --- | --- |
| 网络临时错误、限流 | 限次退避重试；记录费用不确定性 |
| 模型输出格式无效 | 有限结构修正；仍无效则失败或人工介入 |
| 验收失败、明确代码缺陷 | 创建关联的修复任务，不改写原执行结果 |
| 环境缺失、依赖安装失败 | 诊断执行环境，避免一律让业务 Agent 改代码 |
| 需求不清或接口冲突 | blocked，交由 Supervisor 汇总澄清 |
| 越界操作或无效工具身份 | 拒绝并记录，不能通过自动重试绕过 |
| 结果未知 | 核对实际执行；不能证明时暂停 |
| 预算耗尽 | 停止新调用，保存状态并请求处理 |
