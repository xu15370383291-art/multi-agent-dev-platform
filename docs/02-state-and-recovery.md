## 1. 状态分层

| 对象 | 建议状态 | 含义 |
| --- | --- | --- |
| Project | 不另存一套执行状态 | 由当前运行、待审批项和最近交付推导展示状态，避免冲突 |
| WorkflowRun | queued / running / waiting_approval / paused / cancelling / succeeded / failed / cancelled | 一轮工作流的生命周期 |
| Task | pending / ready / running / succeeded / failed / blocked / cancelled | 任务的逻辑状态 |
| TaskExecution | queued / running / succeeded / failed / timed_out / cancelled / unknown | 一次尝试；unknown 表示结果待核对 |
| Integration | not_required / pending / integrating / merged / conflict / failed | 代码成果集成状态 |
| Approval | pending / approved / changes_requested / superseded / cancelled | 某个文档版本的审批 |

paused 必须包含 reason，例如 budget_exhausted、dependency_blocked、recovery_required、change_requested。等待用户审批统一使用 waiting_approval。blocked 是任务状态，不能与运行暂停混用。

2026-10-20已知规划错误修正（docs/23）：多任务scope/interfaces在模型结果解析时提前校验，沿用一次有计量的schema纠正。历史已批准但开发前被拒绝的纯规划运行，可显式请求新架构版本：必须无执行/集成/计划/候选/工作区和活跃或unknown工作，校验原审批/最新版本/摘要/检查点/预算，原审批不改，新版本重新审批；不重放开发工具、不扩预算。该路径不是通用M2恢复。

## 2. 工作流运行转换

| 当前状态 | 触发条件 | 下一状态 |
| --- | --- | --- |
| queued | Worker 成功领取 | running |
| running | 提交版本化审批并形成可恢复检查点 | waiting_approval |
| waiting_approval | 有效决定已保存，恢复工作被领取 | running |
| running | 预算耗尽、需人工处理、恢复存在歧义 | paused |
| paused | 用户作出必要决定或恢复条件满足，显式创建恢复工作 | queued |
| queued / running / waiting_approval / paused | 接受取消请求 | cancelling |
| cancelling | 所有活动执行已终止或已核实不存在 | cancelled |
| running | 系统交付门槛全部通过且交付记录已持久化 | succeeded |
| succeeded / delivered | 用户显式请求docs/60限定追加原AC验收，版本/原交付/无活动及未知结果门禁全部满足 | queued / qa |
| running | 无法恢复的错误或明确终止决定 | failed |

终态不直接改回 running。需要继续时新建关联运行，并明确基线版本。普通检查失败先进入修复或暂停，不立即将整个项目永久判为失败。

2026-10-25用户批准docs/60的窄例外：仅显式请求对原已发布候选的原批准AC追加验收，且原交付/SHA/审批/最新报告/集成基线有效、无活动租约及未知结果时，允许succeeded/delivered→queued/qa，由Worker重新领取并从原持久检查点进入质量节点。旧候选、原脚本/报告与ZIP不变；真实源码缺陷须新任务、新候选、全部原测试及追加测试、独立终审与交付门禁。无源码变化且追加通过只登记新验收并复核原交付，不伪称新源码。一般终态恢复规则继续有效，取消/人工暂停/失租/未知副作用不得借此放行。

## 3. 任务与依赖

- pending → ready：依赖成功，所需代码已经集成，输入版本有效，运行允许执行。
- ready → running：原子领取成功且已创建执行记录。
- running → succeeded：输出协议有效，验收证据齐全，工具结果已核实。
- running → failed：当前尝试失败且结果已确认；重试仍创建新的 TaskExecution。
- failed → ready：错误可重试，预算允许，重试已批准或符合既定策略。
- pending / ready / running / failed → blocked：缺少输入、冲突或需要人工处理；活动进程需先停止或核实。
- blocked → pending / ready：阻塞解除，重新计算依赖。
- 非终态 → cancelled：取消或新计划明确替代该任务；运行中的执行须先停止。

succeeded 和 cancelled 不复用为新一轮尝试。已完成任务需要调整时创建修复任务或新版本任务。调度就绪条件不能只检查依赖的 status=succeeded。

## 4. 数据归属与权威来源

| 信息 | 权威来源 | 其他位置保存什么 |
| --- | --- | --- |
| 项目、运行、任务、执行、审批、预算 | 业务数据库 | State 保存相关 ID、版本和摘要 |
| 工作流执行位置和待恢复中断 | Checkpointer | 数据库保存关联 thread_id、状态及待恢复动作 |
| 代码与集成结果 | Git commit、分支和集成记录 | 数据库保存 SHA 及操作记录 |
| 文档、日志、测试报告、交付包 | 项目工作区或受控产物存储中的具体文件 | 数据库保存引用、摘要、版本或摘要哈希 |
| 对外时间线 | 持久化项目事件 | SSE 传输事件，不作为唯一记录 |

Checkpointer 与业务表不假设天然处于同一个事务。恢复时按已有执行和副作用记录核对，不仅根据图节点位置重跑。

## 5. 持久化动作与可靠投递

建议将业务变化和 outbox 事件/待执行动作在同一个数据库事务中写入，再异步投递。具体队列技术仍待 D05 确认。

关键动作使用幂等键：启动运行、提交审批、创建执行、投递恢复、集成提交和交付生成。重复请求返回已有结果；相同幂等键但不同参数应拒绝。

队列按可能重复投递设计。Worker 通过租约、心跳与执行令牌领取任务；旧 Worker 失去租约后，其状态写入和新工具请求必须被拒绝。启动接管前还须核对旧命令进程，不能只换一个令牌就并发重做。

## 6. 审批暂停与恢复

1. 保存不可变文档版本，记录内容摘要和基线引用。
2. 创建与文档版本、run_id、thread_id 对应的审批项。
3. 工作流进入持久化中断；等待期间释放 Worker 执行资源。
4. API 校验审批仍有效、版本匹配、操作者具备权限。
5. 同一事务保存审批决定和恢复动作。
6. Worker 领取恢复动作，读取检查点，按决定进入后续阶段或文档修改路径。

图中断前后的操作可能重入，文档创建和审批创建必须可去重。审批已保存但图尚未暂停时，恢复动作可以等待检查点就绪，不能丢弃决定或重复启动图。过期版本的审批不能批准新版本。

## 7. 崩溃恢复与结果不确定

| 崩溃位置 | 恢复规则 |
| --- | --- |
| 模型返回前 | 在预算和重试策略内创建新尝试，不声称原调用未计费 |
| 命令执行中 | 根据 execution_id、进程/容器标识查询；仍运行则接管监控或先终止 |
| 命令结束但业务结果未保存 | 读取持久化执行日志和退出结果，核实后补记 |
| Git 已合并但任务记录未更新 | 核对集成操作 ID、目标 SHA 和分支历史，再补记结果 |
| 审批已保存但恢复未执行 | 由 outbox 重投，幂等恢复 |
| 交付文件已生成但记录未完成 | 核对 manifest 和内容摘要，完成登记或受控重建 |

无法确认副作用时标记 unknown 并暂停相关执行，不盲目重放删除、安装脚本、提交或合并。恢复只接管非终态工作，不重跑整个项目。

## 8. 取消与超时

C2—C5实现增量见docs/20：除Task/Tool外，IntegrationRecord、RunWorkspace、Candidate或质量报告存在unknown也阻止新派发；已知冲突以新版本计划中的解决任务处理，不能抹掉原冲突。计划替代前无活动执行，架构变动必须生成新文档审批。源码修复是新任务/执行/候选的业务流程，不是重放旧失败工具。全量恢复仍为M2；四任务真实验收到30次预算时确实暂停，用户随后明确授权仅此运行30→45，已核对确定副作用与快照后执行并审计；已消耗调用不重置，其他运行仍默认30，未提供通用自动恢复。动态子图显式不继承父节点调用位置检查点，父主图PostgresSaver和业务持久账本保留，当前执行身份和unknown核对门槛不放宽。

- 接受取消后先停止调度新任务，并使待审批项失效。
- 向活动模型请求、工具和进程发送停止信号；超过宽限期后终止可控进程。
- 终止任务所属进程树或容器执行单元，避免杀掉其他任务共享的服务。
- 核实无活动执行后才进入 cancelled；终止失败时保留 cancelling 和诊断信息。
- 保留已经产生的代码、日志和历史；取消不等于删除工作区。
- 命令、任务、模型调用和运行预算分别设限；超时结果应归类，不能全当成业务缺陷。
