## 3. M1：单开发任务的真实闭环

前置：M0 完成。

实现范围：

- 工程初始化、最小数据表、持久化执行入口与项目工作区。
- 最小 API：创建项目、启动运行、查询状态、读取文档、提交审批。
- 简易模型配置页面：填写 Key、Base URL、模型类型/型号，测试连接、选择默认配置，并在任务执行时保存配置快照。
- Supervisor → Product → PRD 审批 → Architect → 架构审批。
- 一个 Game Developer 开发任务，调用真实文件、命令和 Git 工具。
- 固定候选版本、真实构建与浏览器验证、独立 Reviewer、交付记录。
- 最小预算、超时、工具记录、路径边界和幂等校验。

首个用例建议为小型 2048：方向输入、移动与合并、分数、重新开始、最高分保存。具体规则以示例 PRD 为准。

门槛：两次审批可修改和重提；批准前不进入下阶段；单任务生成的游戏能实际运行；QA 与 Reviewer 检查同一版本；交付包可按说明启动。可以先通过 API 或简易开发页面操作。

不将仅有模拟节点的演示认定为 M1 通过。模拟模型和工具只用于协议及异常测试。

- 取消后不再调度新任务，活动进程被核实停止，日志和代码保留。
- 预算耗尽后不通过新建修复任务继续消耗。

## 5. M3：DAG、并行集成与修复

前置：M1；先通过 docs/18 C0 的必要执行保护，不再等待完整 M2。进入并行前明确 D08、D10、D12，并验证租约隔离、预算预留、稳定执行身份及工作区边界。通用自动接管未完成时，未知结果暂停核实。

实现范围：

- 计划版本、依赖校验、就绪任务调度和并发额度。
- 至少两个独立 worktree 的并行开发任务。
- 统一集成队列、冲突任务、集成验证与 Candidate 记录。
- QA 与 Reviewer 并行，修复后新候选的重新验证。
- 需求到证据的覆盖矩阵和确定性交付门槛。
- 接入 Web Developer，并完成一个小型 Web 软件闭环。

门槛：

- 无环校验、非法角色、缺失依赖和过期输入均可阻止错误调度。
- 两个独立任务可并行；依赖任务等待必要集成完成。
- 同时修改同一关键文件的用例进入明确冲突处理，不丢失变更。
- 有意引入功能缺陷，系统产生修复任务，新版本经重新检查后交付。
- 任一必要验收项 not_verified 或报告版本错误时不能通过交付门槛。
