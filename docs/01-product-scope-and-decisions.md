## 1. 目标与两类项目

平台自身是多智能体开发平台；用户通过平台生成的应用是业务项目。两者的技术栈、运行目录、数据和生命周期应分别设计。

V1 的目标是可追踪、可审批、可恢复地完成一个小型业务项目。首个验收示例建议使用浏览器版 2048；随后增加一个简单 Web 软件示例，验证两种项目类型。

2048 只是验收用例，不能成为所有项目硬编码的任务模板。

## 3. 建议的 V1 产品闭环

1. 创建项目并保存自然语言需求。
2. 显示 Supervisor 的阶段计划。
3. 生成 PRD；支持批准、填写修改意见和查看历史版本。
4. 生成架构及任务计划；支持相同的审批交互。
5. 校验计划，执行开发，展示任务及工具执行进度。
6. 集成代码，生成候选版本，执行 QA 和 Reviewer 检查。
7. 根据结果修复、暂停请求用户处理，或交付。
8. 展示源代码包、预览入口、测试和审查报告、已知问题。
9. 支持取消运行，以及重启后的状态查询和受控恢复。
10. 用户可维护多份模型配置、验证连接、选择默认模型并切换 Agent 使用的配置。

建议第一版提供项目列表、项目工作台、任务详情和交付查看能力。审批可在工作台中完成，不必独立成多个页面。视觉风格和具体布局另行设计。

## 4. 建议控制范围

- 已确认：先供个人使用，在当前 Windows 本机运行，用 Docker 执行业务项目；暂不做注册和团队功能。
- 首个里程碑只执行一个开发任务，后续里程碑补齐 DAG 并行；最终 V1 保留并行能力。
- 先支持新建项目；已有仓库导入、远程推送和交付后持续迭代另行确定。
- 已批准需求在一轮正式开发中保持稳定。新增需求先记录为变更请求，完成影响评估后决定如何执行。
- 团队协作、计费、跨项目知识库、插件市场和分布式集群不作为当前建议的 V1 目标。

除明确标注已确认的内容外，上述仍为范围建议。即使先服务个人，多项目数据和工作区也不能串用。

## 7. 需求变更建议规则

- 文档修订生成新版本，历史版本不可覆盖。
- 批准前的修改由对应文档 Agent 处理。
- 批准后的变更先建立 change_request，记录原因、范围及影响。
- 有效批准基线暂不被替换；先暂停受影响的执行，再评估文档、任务、代码和证据的失效范围。
- 需要改变 PRD 或架构时重新审批；批准后启用新计划，旧任务保留执行历史。
- 可复用的代码和证据必须明确标记适用版本，不自动继承通过结论。

继续开发、新一轮运行与原运行修订之间的产品交互，在 D11 中确定。
